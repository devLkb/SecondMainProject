# PetChain 체인코드 ↔ 백엔드 연동 가이드 (VirtualBox / Ubuntu)

이 문서는 `chaincode/petchain` (Hyperledger Fabric, Go) 체인코드를 **VirtualBox 우분투 VM**에서
띄우고, 우리 Spring Boot 백엔드와 실제로 연결하는 전체 과정을 단계별로 정리한 것이다.

전제: Windows 호스트에는 Docker/Go가 없으므로 **Fabric 네트워크와 체인코드 실행은 VM 안에서** 한다.
백엔드는 VM 안에서 같이 실행하거나, 호스트에서 실행하고 VM의 peer에 접속한다(아래 7장 네트워크 옵션 참고).

> 핵심 원칙: 체인코드는 **원문을 저장하지 않고 해시/상태만** 저장한다. 우리 백엔드는 이미
> `HashContract`로 `sha256:<hex>` 해시를 만들고 있어서( [HashContract.java](../be/backend/src/main/java/com/blockchain/backend/common/HashContract.java) )
> 체인코드 인자 형식과 그대로 맞는다. 따라서 연동은 "해시 계산"이 아니라 "트랜잭션 호출 배선" 작업이다.

---

## 0. 연동 지도 (무엇을 언제 호출하나)

| 백엔드 흐름 | 진입 지점(서비스) | 호출할 체인코드 함수 |
| --- | --- | --- |
| 병원 진료기록 등록 | `RecordService.createRecord` | `RegisterRecord` |
| 보호자 동의 등록 | `ConsentService` (동의 토글 ON) | `RegisterConsent` |
| 제출 생성 | `SubmissionService` | `CreateSubmissionWithConsent` |
| 검증 실패/차단 | `VerificationService` | `RecordVerification` |
| 검증 성공(+포인트차감+크레딧적립) | `VerificationService` | `ProcessSuccessfulVerification` |
| 결제 완료 포인트 충전 | `PointService` | `ConfirmPointPurchase` |
| 포인트 잔액 조회 | `PointService` | `GetPointBalance` |

함수 시그니처·인자 형식의 원본은 [BACKEND_INTEGRATION_GUIDE.md](../BACKEND_INTEGRATION_GUIDE.md),
CLI 배포·시연은 [chaincode/petchain/DEPLOY_DEMO.md](../chaincode/petchain/DEPLOY_DEMO.md) 참고.

## 1. VirtualBox VM 준비

- 이미지: **Ubuntu Server/Desktop 22.04 LTS** (x86_64)
- 사양: **CPU 2코어 / RAM 4GB 이상 / 디스크 40GB+** (Fabric 컨테이너 여러 개 + 빌드)
- 네트워크: 기본 NAT + **포트 포워딩** 또는 **호스트 전용 어댑터** 추가
  - 백엔드를 호스트(Windows)에서 돌리고 VM의 peer에 붙으려면 peer 포트(7051 등)를 호스트로
    포워딩하거나 호스트 전용 어댑터로 VM IP를 고정한다.
  - 가장 단순한 방법은 **백엔드도 VM 안에서 실행**하는 것(localhost 로 peer 접속).
- 저장소 가져오기(VM 안에서):
  ```bash
  sudo apt update && sudo apt install -y git
  git clone <레포 URL> ~/pointpro
  cd ~/pointpro
  ```

### ⚠️ MSP 이름 주의 (가장 흔한 실패 원인)

체인코드 권한 상수는 `PlatformOrgMSP`, `HospitalOrgMSP`, `InsurerOrgMSP`(+`InsuranceAOrgMSP`,
`InsuranceBOrgMSP`)인데, test-network 기본 조직은 `Org1MSP`, `Org2MSP`다. 그대로 invoke 하면
`MSP Org1MSP is not allowed`가 난다. 두 가지 길:

| 방식 | 설명 | 추천 |
| --- | --- | --- |
| **A. 데모용: 체인코드 MSP 상수를 맞춤** | 임시 브랜치에서 [main.go](../chaincode/petchain/main.go) 의 `platformMSP="Org1MSP"`, `insurerMSP="Org2MSP"` 등으로 바꿔 재배포 | 로컬에서 빠르게 end-to-end 보고 싶을 때 |
| **B. 운영형: MSP 이름 맞춘 커스텀 네트워크** | `PlatformOrgMSP/HospitalOrgMSP/Insurance*OrgMSP`로 조직을 구성한 네트워크 | 실제 다조직 데모 |

> 처음엔 **A**로 동작을 확인하고, 그다음 B로 넘어가는 걸 권장한다.
> 단일 `petchannel`은 가이드상 "공유 채널"처럼 동작하므로 보험사 전용 채널 분리 없이 데모가 된다.

### 6-6. 실제 Fabric Gateway 구현 `FabricGatewayLedger.java`
```java
package com.blockchain.backend.chain;

import io.grpc.ManagedChannel;
import io.grpc.netty.shaded.io.grpc.netty.GrpcSslContexts;
import io.grpc.netty.shaded.io.grpc.netty.NettyChannelBuilder;
import org.hyperledger.fabric.client.*;
import org.hyperledger.fabric.client.identity.*;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.stereotype.Component;

import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.security.PrivateKey;
import java.security.cert.X509Certificate;
import java.util.stream.Stream;

@Component
@ConditionalOnProperty(name = "chain.enabled", havingValue = "true")
public class FabricGatewayLedger implements PetChainLedger {

    private final Gateway gateway;
    private final Contract contract;

    public FabricGatewayLedger(ChainProperties props) throws Exception {
        // 1) peer 로 향하는 gRPC(TLS) 채널
        var tls = GrpcSslContexts.forClient()
                .trustManager(Files.newInputStream(Path.of(props.getTlsCertPath()))).build();
        ManagedChannel channel = NettyChannelBuilder
                .forTarget(props.getPeerEndpoint())
                .sslContext(tls)
                .overrideAuthority(props.getPeerHostOverride())
                .build();

        // 2) 클라이언트 신원(X.509 인증서 + 개인키) + MSP
        X509Certificate cert;
        try (var r = Files.newBufferedReader(Path.of(props.getCertPath()))) {
            cert = Identities.readX509Certificate(r);
        }
        Identity identity = new X509Identity(props.getMspId(), cert);

        PrivateKey pk;
        Path keyFile;
        try (Stream<Path> s = Files.list(Path.of(props.getKeyDir()))) {
            keyFile = s.findFirst().orElseThrow(); // keystore 안의 *_sk
        }
        try (var r = Files.newBufferedReader(keyFile)) {
            pk = Identities.readPrivateKey(r);
        }
        Signer signer = Signers.newPrivateKeySigner(pk);

        // 3) Gateway 연결 → 채널/체인코드 컨트랙트
        this.gateway = Gateway.newInstance()
                .identity(identity).signer(signer).connection(channel).connect();
        this.contract = gateway.getNetwork(props.getChannel()).getContract(props.getChaincode());
    }

    public boolean isEnabled() { return true; }

    private String submit(String fn, String... args) {
        try {
            byte[] result = contract.submitTransaction(fn, args);
            return new String(result, StandardCharsets.UTF_8);
        } catch (Exception e) {
            throw new RuntimeException("chaincode submit 실패: " + fn + " — " + e.getMessage(), e);
        }
    }
    private String eval(String fn, String... args) {
        try { return new String(contract.evaluateTransaction(fn, args), StandardCharsets.UTF_8); }
        catch (Exception e) { throw new RuntimeException("chaincode query 실패: " + fn, e); }
    }

    public String registerRecord(String recordId, String hospitalId, String recordHash, String attachJson, String createdAt) {
        return submit("RegisterRecord", recordId, hospitalId, recordHash, attachJson, createdAt);
    }
    public String registerConsent(String consentId, String recordId, String insurerId, String guardianHash, String validUntil, String createdAt) {
        return submit("RegisterConsent", consentId, recordId, insurerId, guardianHash, validUntil, createdAt);
    }
    public String createSubmissionWithConsent(String subId, String recordId, String consentId, String hospitalId, String insurerId, String recordHashAtSubmit, String createdAt) {
        return submit("CreateSubmissionWithConsent", subId, recordId, consentId, hospitalId, insurerId, recordHashAtSubmit, createdAt);
    }
    public String recordVerification(String verId, String subId, String status, String failJson, String recordHashAtVerify, String consentSnapshot, String verifiedAt, String auditLogId) {
        return submit("RecordVerification", verId, subId, status, failJson, recordHashAtVerify, consentSnapshot, verifiedAt, auditLogId);
    }
    public String processSuccessfulVerification(String verId, String subId, String recordHashAtVerify, String consentSnapshot, String verifiedAt, String auditLogId, String idem) {
        return submit("ProcessSuccessfulVerification", verId, subId, recordHashAtVerify, consentSnapshot, verifiedAt, auditLogId, idem);
    }
    public String confirmPointPurchase(String pid, String insurerId, String amount, String paymentId, String orderId, String paidAt, String by, String idem) {
        return submit("ConfirmPointPurchase", pid, insurerId, amount, paymentId, orderId, paidAt, by, idem);
    }
    public long getPointBalance(String insurerId) {
        String raw = eval("GetPointBalance", insurerId);
        try { return Long.parseLong(raw.replaceAll("[^0-9-]", "")); } catch (Exception e) { return 0L; }
    }
}
```

> 버전 주의: `fabric-gateway` 패키지/클래스명은 SDK 버전에 따라 다를 수 있다. VM에서 빌드하며
> import가 맞는지 확인한다. (gRPC는 `io.grpc.netty.shaded` 셰이드 버전을 사용)

### 6-7. 기존 흐름에 배선 — RecordService 예시(레퍼런스)

[RecordService.createRecord](../be/backend/src/main/java/com/blockchain/backend/petchainAPI/service/RecordService.java) 의
`autoCreateClaimPackages(...)` 호출 **다음**에 추가한다. 백엔드가 이미
`recordId`, `detailDataHash`(=recordHash, `sha256:` 형식), 첨부 해시를 갖고 있으므로 그대로 넘긴다.

```java
// 필드 주입
private final PetChainLedger chainLedger;

// createRecord(...) 끝부분, return 직전
if (chainLedger.isEnabled()) {
    try {
        // 첨부 해시 JSON 배열: ["sha256:..","sha256:.."]
        String attachJson = fileHashes.stream()
                .map(h -> "\"" + h.hash() + "\"")
                .collect(java.util.stream.Collectors.joining(",", "[", "]"));
        String createdAtIso = (saved.getCreatedAt() != null)
                ? saved.getCreatedAt().toInstant(java.time.ZoneOffset.UTC).toString()
                : java.time.Instant.now().toString();
        chainLedger.registerRecord(
                saved.getRecordId(),
                String.valueOf(hospital.getId()),
                saved.getDetailDataHash(),     // 이미 sha256:<hex>
                attachJson,
                createdAtIso);
        // 성공 시 온체인 상태 표시(선택)
        // saved.setOnChainStatus("REGISTERED");
    } catch (Exception e) {
        // 온체인 실패해도 오프체인 진료기록은 유지하고 로그만 남긴다(보상은 별도 잡으로).
        org.slf4j.LoggerFactory.getLogger(RecordService.class)
                .warn("RegisterRecord 온체인 반영 실패 (recordId={}): {}", saved.getRecordId(), e.getMessage());
    }
}
```

### 6-8. 나머지 흐름 배선 (같은 패턴)

| 서비스 | 호출 | 인자 매핑 메모 |
| --- | --- | --- |
| `ConsentService` 동의 ON | `registerConsent` | `consentId`, `recordId`, `insurerId`, `guardianHashedId`(보호자ID는 원문 대신 `HashContract.hashCanonical`로 해시), `validUntil`(ISO), `createdAt`(ISO) |
| `SubmissionService` 생성 | `createSubmissionWithConsent` | `submissionId`, `recordId`, `consentId`, `hospitalId`, `insurerId`, `recordHashAtSubmit`(제출 시점 record의 `detailDataHash`), `createdAt` |
| `VerificationService` 실패/차단 | `recordVerification` | `status`는 `FAILED`/`BLOCKED`, `failureReasonsJson`은 사유 배열 |
| `VerificationService` 성공 | `processSuccessfulVerification` | `verifiedAt`(ISO), `auditLogId`, **`idempotencyKey`**(재시도는 같은 키, 새 성공은 새 키) |
| `PointService` 충전 | `confirmPointPurchase` | `paymentId`/`orderId`/`purchaseId` 중복은 백엔드 DB에서도 별도 차단 |

> 모든 호출은 `if (chainLedger.isEnabled()) { try { ... } catch ... }` 로 감싸 오프체인 경로를
> 절대 막지 않게 한다. 온체인 반영 실패는 로그+보상 잡으로 처리.


### 연결 확인
1. 백엔드 기동 로그에 Fabric Gateway 연결 에러가 없는지 확인.
2. 병원 계정으로 진료기록을 등록한 뒤, VM에서 온체인 반영을 조회:
   ```bash
   peer chaincode query -C petchannel -n petchain \
     -c '{"function":"GetRecordHash","Args":["<백엔드가 발급한 recordId>"]}'
   ```
   백엔드가 저장한 `detailDataHash`와 동일한 `sha256:...`가 나오면 **연결 성공**.

## 8. 트러블슈팅

| 증상 | 원인 / 해결 |
| --- | --- |
| `MSP Org1MSP is not allowed` | 체인코드 MSP 상수와 네트워크 MSP 불일치 → 4장 방식 A/B로 정렬 |
| `claim operation is not allowed on governance-channel` | governance-channel에서 청구/검증 호출 금지 → `petchannel` 사용 |
| `record ... hash does not match submitted hash` | 제출 시점 hash와 원장 hash 불일치 → 제출에 record의 현재 `detailDataHash` 전달 |
| `consent ... is not ACTIVE` | 동의 철회/만료 → 동의 상태 먼저 확인 |
| `insufficient points for insurer ...` | 보험사 포인트 부족 → `IssuePoints`/`ConfirmPointPurchase`로 충전 |
| `... already exists` (recordId/consentId/...) | 중복 ID → 백엔드 ID 생성 규칙 점검, 테스트면 `network.sh down && up`으로 원장 초기화 |
| 백엔드 기동 시 gRPC/TLS 에러 | `CHAIN_*` 경로(특히 `keystore`의 `*_sk`)와 `peer-host-override` 확인 |

날짜는 전부 **ISO-8601**(`2026-05-15T00:01:00.000Z`), 해시는 전부 **`sha256:<64 hex>`** 여야 한다.
`idempotencyKey`는 5분 윈도우라 영구 중복 방지가 아니므로 백엔드 DB에서 `paymentId/orderId`를
영구적으로 별도 관리해야 한다.
