# PetChain MVP 범위 정의

작성일: 2026-05-15  
근거 문서: `.omx/plans/PetChain.md`  
목적: 기존 기획서의 MVP 범위가 넓어 구현 우선순위를 좁히고, 1차 구현에서 반드시 만들 것과 만들지 않을 것을 명확히 고정한다.

---

## 1. MVP 한 줄 정의

PetChain MVP는 **보호자 동의를 받은 동물병원 진료기록과 제출 요청을 플랫폼에 등록하고, 보험사가 플랫폼 API 또는 화면을 통해 검증 완료 제출 패키지를 조회하며, 추가 검증이 필요한 경우 검증 API로 비식별 진료 검증 데이터를 확인하는 최소 청구 검증 흐름**이다.

MVP는 보험 상품 판매, 보험 가입 중개, 보험금 산정, NFT/SBT 발급을 포함하지 않는다. 다만 **PetChain Point 기반 B2B 검증 크레딧**은 MVP에 포함한다.

---

## 2. 현재 확정된 범위 결정

| 결정 항목 | MVP 기준 |
| --- | --- |
| 진료기록 전송 대상 | 병원이 보호자 동의를 받은 진료기록과 제출 요청만 플랫폼에 등록하고, 보험사는 플랫폼이 검증 통과 처리한 제출 패키지를 조회한다. |
| 데이터 흐름 | MVP 구현상 `병원 -> 내부 시스템/플랫폼 -> 보험사` 흐름으로 둔다. “병원 -> 보험사”는 업무상 제출 관계를 의미한다. |
| 플랫폼 역할 | 직접 보험 심사를 하지 않고, 제출 요청·동의·대상 보험사·기록 무결성·제출 가능 상태를 검증하고 제출 패키지/검증 API 접근 권한을 통제한다. |
| 보험사 역할 | 플랫폼 API 또는 화면에서 검증 완료 제출 패키지를 조회하고, 검증 API를 호출해 비식별 진료 검증 데이터를 확인한 뒤 보험사 내부 시스템에서 심사한다. |
| 보호자 역할 | 특정 진료기록을 특정 보험사에 제출하도록 동의한다. |
| NFT/SBT | MVP에서 제외한다. |
| 포인트/크레딧 | MVP에 포함한다. 보호자 리워드가 아닌 보험사/병원 간 B2B 내부 검증 크레딧으로만 사용하며, 병원 크레딧은 고급 SaaS 기능 또는 자체 웹사이트 배너 홍보 요청 시 차감/소각한다. |

## 3. MVP에 포함하는 기능

### 3.1 병원 기능

- 병원 계정 로그인
- 보호자/반려동물 최소 정보 조회 또는 입력
- 진료기록 등록
- 진료기록 원문 또는 파일의 해시 생성
- 보호자 동의가 있는 진료기록만 제출 요청 생성
- 제출 요청 상태 확인

### 3.2 보호자 동의 기능

- 보호자 식별
- 특정 진료기록 단위의 제출 동의
- 특정 보험사 대상 동의
- 동의 유효기간 1년 적용
- 동의 상태 저장
- 동의 철회
- 동의 철회 후 신규 제출/조회 차단

동의 유효기간은 1년이다. 동의 철회 또는 유효기간 만료 후에는 신규 제출, 제출 패키지 신규 조회, 원문/첨부 신규 접근, 검증 API를 통한 비식별 진료 검증 데이터 신규 조회를 차단한다. 철회 시 플랫폼의 제출 패키지는 삭제하되, Hyperledger Fabric에 남은 검증 데이터와 해시/감사 이력은 삭제하지 않는다. 이미 보험사가 조회하거나 다운로드한 자료는 회수 또는 무효화하지 않는다. 철회 후 재동의는 허용한다.

### 3.3 플랫폼 검증 기능

- 제출 요청 수신
- 보호자 동의 여부 검증
- 제출 대상 보험사 검증
- 진료기록 해시 검증
- 진료기록 제출 이력 저장
- 검증 결과 생성
- 검증 성공 건만 보험사 전달 가능 상태로 변경

### 3.4 보험사 기능/API

- 보험사 계정 또는 API 인증
- 검증 완료 제출 패키지 조회
- 제출 패키지 다운로드 또는 조회
- 검증 API를 통한 비식별 진료 검증 데이터 조회
- 검증 API 호출 시 포인트 잔액 확인
- 검증 API가 성공하고 비식별 진료 검증 데이터가 정상 반환된 경우에만 포인트 1점 차감
- 동일 제출 요청 반복 검증 API 성공 호출 시 매번 포인트 차감
- 보험사 내부 심사 결과 상태 기록

### 3.5 포인트/크레딧 기능

- Platform Org의 보험사 포인트 발행
- 보험사 포인트 잔액 조회
- 보험사 검증 API 호출 시 포인트 차감
- 검증 API 성공 호출에 대한 병원 운영 크레딧 1점 적립
- 동일 제출 요청 반복 검증 API 성공 호출 시 매번 병원 운영 크레딧 적립
- 병원 크레딧을 고급 SaaS 기능 사용 또는 자체 웹사이트 배너 홍보 요청 시 차감/소각 처리
- 포인트 발행/차감/적립/소각 이력 조회

MVP 포인트/크레딧은 외부 결제수단, 현금성 리워드, 보호자 보상으로 사용하지 않는다. 병원 크레딧 사용처는 고급 SaaS 기능과 자체 웹사이트 배너 홍보로 제한한다.

포인트/크레딧 발생 기준:

- 검증 API를 시도하기만 해서는 보험사 포인트를 차감하지 않는다.
- 검증 API가 성공하고 비식별 진료 검증 데이터가 정상 반환된 경우에만 보험사 포인트 1점을 차감한다.
- 동일 제출 요청을 반복 호출해도 매번 성공 응답이 반환되면 매번 보험사 포인트를 차감한다.
- 검증 실패, 권한 없음, 포인트 부족 응답은 과금 대상이 아니다.
- 제출 패키지 조회와 검증 API 호출은 별도로 과금하지 않는다.
- 검증 API 성공 호출이 발생하면 해당 제출 건의 병원에 운영 크레딧을 적립한다.
- 동일 제출 요청 반복 검증 API 성공 호출도 매번 병원 운영 크레딧 적립 대상이다.
- 병원 크레딧은 고급 SaaS 기능 사용 또는 자체 웹사이트 배너 홍보 요청 시 차감/소각한다.

### 3.6 관리자/운영 기능

- 병원 계정 관리
- 보험사 계정 관리
- 진료기록 제출 이력 조회
- 검증 실패 사유 조회
- 포인트 잔액 및 거래 이력 조회
- 감사 로그 조회

## 4. MVP에서 제외하는 기능

| 제외 기능 | 제외 이유 |
| --- | --- |
| NFT 발급 | 현재 확정 결정상 MVP 제외. 검증 흐름 증명에는 DB/로그로 충분하다. |
| SBT 발급 | 반려동물 신원 토큰화는 핵심 제출 흐름 검증 이후로 미룬다. |
| 보험상품 추천·비교·판매 | 보험모집 리스크가 있으며 서비스 목적과 다르다. |
| 보험 가입 중개 | MVP는 이미 가입된 보험 청구 검증만 다룬다. |
| 보험금 산정 | 보험사 고유 업무이므로 플랫폼은 수행하지 않는다. |
| 보험금 지급 여부 판단 | 보험사 고유 업무이므로 플랫폼은 수행하지 않는다. |
| 보호자 대상 포인트 지급 | 포인트는 B2B 내부 검증 크레딧이며 보호자 리워드가 아니다. |
| 포인트 현금 환급/외부 가맹점 사용 | 전자금융 리스크를 줄이기 위해 내부 차감·정산 용도로 제한한다. |
| 다중 병원/다중 보험사 확장 | 1차는 1개 병원, 1개 보험사 기준으로 구현한다. |
| 병원 SaaS 전체 고도화 | MVP는 제출 흐름 검증용 최소 화면을 우선하되, 병원 크레딧 차감/소각 대상이 되는 고급 SaaS 기능의 사용권 또는 차감 이력은 최소 범위로만 다룬다. |
| 전체 통계/BI 대시보드 | 운영 검증 이후 2차 범위로 둔다. |
| 자동 표준 코드 매핑 | MVP는 제한된 코드 목록 또는 수동 입력으로 처리한다. |

## 5. MVP 기준 사용자 흐름

### 5.1 정상 흐름

1. 병원이 진료기록을 등록한다.
2. 플랫폼이 진료기록 원문 또는 첨부 파일의 해시를 저장한다.
3. 보호자가 특정 진료기록을 특정 보험사에 제출하도록 동의한다.
4. 병원이 해당 진료기록의 보험사 제출을 요청한다.
5. 플랫폼이 동의 상태, 제출 대상 보험사, 진료기록 해시를 검증한다.
6. 플랫폼이 보험사 조회 가능 상태의 제출 패키지를 만든다.
7. 보험사가 플랫폼 API 또는 화면에서 검증 완료 제출 패키지를 조회한다.
8. 보험사가 검증 API를 호출할 때 포인트 잔액을 확인한다.
9. 검증 API가 성공하고 비식별 진료 검증 데이터가 정상 반환되면 보험사 포인트를 차감하고 병원 운영 크레딧을 적립한다. 동일 제출 요청의 반복 성공 호출도 매번 차감/적립한다.
10. 보험사는 자체 시스템에서 보험금 산정과 지급 여부를 판단한다.
11. 플랫폼은 제출, 조회, 검증, 포인트 거래, 심사 상태 변경 이력을 감사 로그로 남긴다.

### 5.2 실패 흐름

- 보호자 동의가 없으면 제출 요청을 거절한다.
- 동의 대상 보험사와 요청 보험사가 다르면 제출 요청을 거절한다.
- 진료기록 해시가 등록 시점과 다르면 제출 요청을 거절한다.
- 보험사 포인트 잔액이 부족하면 검증 API 호출을 거절하고 포인트를 차감하지 않는다.
- 검증 실패, 권한 없음, 포인트 부족 응답은 과금/크레딧 적립 대상이 아니다.
- 보호자가 동의를 철회하거나 동의 유효기간 1년이 만료되면 보험사의 제출 패키지 신규 조회와 검증 API 신규 조회를 차단한다.
- 보험사는 검증 실패 건의 원문 진료기록을 조회할 수 없다.

## 6. MVP 데이터 범위

### 6.1 저장하는 데이터

- 병원 계정
- 보험사 계정
- 보호자 최소 식별 정보
- 반려동물 최소 정보
- 보험 가입 정보 또는 보험사 식별 정보
- 진료기록 메타데이터
- 진료기록 원문/첨부 파일 저장 위치
- 진료기록 해시
- 보호자 동의 이력
- 제출 요청
- 플랫폼 검증 결과
- 제출 패키지
- 보험사 조회 이력
- 포인트 잔액
- 포인트 거래 이력
- 감사 로그

#### 6.1.1 MVP 제출 패키지

제출 패키지는 보험사가 심사·확인을 위해 조회하는 검증 완료 묶음이다. 제출 패키지 조회 자체는 별도 과금하지 않는다.

필수 포함 항목:

- `submissionId`
- `verificationId`
- `recordId`
- 진료기록 원문 접근 URL
- 첨부 파일 목록 및 첨부 파일 접근 URL
- 진료기록 해시
- 첨부 파일별 해시
- 검증 결과
- 동의 스냅샷
- 병원 최소 정보
- 보호자 최소 식별 정보
- 반려동물 최소 정보
- 제출 요청 시각
- 검증 완료 시각
- 감사 로그 ID

검증 API 응답은 제출 패키지 전체가 아니라 비식별 진료 검증 데이터와 무결성 대조 정보로 제한한다. 제출 패키지도 원문/첨부 본문을 직접 포함하지 않고 단기 서명 URL만 제공하며, 검증 API를 통해 원문 진료기록 또는 첨부 파일 본문을 반환하지 않는다.

### 6.2 온체인 또는 블록체인 검증 범위

MVP에서 블록체인을 구현하는 경우에도 온체인에는 원문 개인정보를 저장하지 않는다. 저장 대상은 다음으로 제한한다.

- 진료기록 식별자
- 진료기록 해시
- 병원 식별자
- 보험사 식별자
- 동의 상태 또는 동의 이벤트 해시
- 검증 결과
- 포인트 차감/적립 이벤트 식별자
- 감사 로그 식별자

블록체인 구현이 일정상 부담이 될 경우, 1차 MVP에서는 동일한 검증 계약을 DB 기반 감사 로그로 먼저 구현하고, 블록체인 연동은 후속 단계로 분리할 수 있다.

### 6.3 포인트 데이터 범위

MVP 포인트 데이터는 다음 수준으로 제한한다.

- 보험사 포인트 잔액
- 병원 운영 크레딧 잔액
- 검증 API 성공 호출별 포인트 차감 이력
- 검증 API 성공 호출별 병원 크레딧 적립 이력
- 발행, 차감, 적립, 소각 거래 이력
- 거래 발생 주체
- 연결된 검증 요청 또는 진료기록 식별자
- 거래 시각

포인트는 보험 가입 건수, 보험료, 보험금 지급액, 청구 승인 성공 여부와 연결하지 않는다. 제출 패키지 조회는 별도 과금하지 않으며, 검증 API 성공 호출만 포인트 차감 및 병원 크레딧 적립 이벤트가 된다.

## 7. 최소 화면/API 범위

| 영역 | MVP 산출물 |
| --- | --- |
| 병원 화면 | 진료기록 등록, 제출 요청, 제출 상태 확인 |
| 보호자 화면 | 제출 동의, 동의 철회, 동의 상태 확인 |
| 보험사 화면/API | 검증 완료 기록 조회, 제출 패키지 조회, 검증 API를 통한 비식별 진료 검증 데이터 조회, 포인트 잔액 조회, 심사 상태 기록 |
| 관리자 화면 | 기관 계정 관리, 제출/검증 이력 조회, 포인트 거래 이력 조회 |
| 플랫폼 API | 진료기록 등록, 동의 등록/철회, 제출 요청, 제출 패키지 조회, 검증 API, 검증 결과 조회, 보험사 조회, 포인트 발행/차감/적립/소각/이력 조회 |

## 8. MVP 성공 기준

MVP는 아래 조건을 만족하면 완료로 본다.

- 병원이 진료기록을 등록할 수 있다.
- 보호자가 특정 진료기록과 특정 보험사에 대해 동의할 수 있다.
- 동의 없는 진료기록은 보험사로 전달되지 않는다.
- 동의 대상이 아닌 보험사는 진료기록을 조회할 수 없다.
- 플랫폼이 진료기록 해시를 비교해 위변조 여부를 판별할 수 있다.
- 검증 성공 건만 보험사가 조회할 수 있다.
- 보험사는 포인트 잔액이 있어야 검증 API를 호출할 수 있다.
- 검증 API가 성공하고 비식별 진료 검증 데이터가 정상 반환된 경우에만 보험사 포인트가 차감된다.
- 동일 제출 요청 반복 검증 API 성공 호출도 매번 보험사 포인트 차감 대상이다.
- 검증 API 성공 호출 시 병원 운영 크레딧 1점이 적립된다.
- 동일 제출 요청 반복 검증 API 성공 호출도 매번 병원 운영 크레딧 적립 대상이다.
- 포인트 발행/차감/적립/소각 이력이 조회 가능하다.
- 검증 실패 사유가 기록된다.
- 모든 제출/조회/검증 이벤트가 감사 로그로 남는다.
- 보험금 산정과 지급 판단은 플랫폼 밖에서 수행된다.
- NFT/SBT 관련 화면, API, 테이블, 체인코드는 구현하지 않는다.
- 포인트/크레딧은 보호자에게 지급하지 않고, 현금 환급이나 외부 사용을 허용하지 않는다.
- 병원 크레딧은 고급 SaaS 기능 또는 자체 웹사이트 배너 홍보 요청 시 차감/소각할 수 있다.

## 11. "검증이 필요한 단계" 정의 의견

"병원 -> 보험사로 가되, 검증은 우리 플랫폼을 거친다"는 표현은 팀원마다 다르게 해석될 수 있으므로, MVP 문서에서는 "검증이 필요한 단계"를 물리적인 데이터 중계 단계가 아니라 **보험사 전달 전 제출 적격성 검증 게이트**로 정의한다.

권장 정의는 다음과 같다.

> 검증이 필요한 단계란, 병원이 보호자 동의를 받은 진료기록을 보험사에 제출하기 전에 플랫폼이 반드시 확인해야 하는 제출 적격성 검사 구간을 말한다. 플랫폼은 보험 심사, 보험금 산정, 지급 판단을 하지 않고, 보험사가 기록을 조회하기 전에 제출 동의와 기록 신뢰성을 확인하는 게이트 역할만 수행한다.

MVP에서 플랫폼 검증 게이트는 아래 4개 항목으로 한정한다.

### 11.1 제출 동의 검증

보호자가 해당 진료기록을 특정 보험사에 제출하는 데 동의했는지 확인한다.

확인 항목:

- 보호자 식별
- 진료기록 단위 동의 여부
- 동의 대상 보험사
- 동의 철회 여부
- 동의 생성/철회 시각

### 11.2 제출 대상 보험사 검증

보호자가 동의한 보험사와 병원이 실제 제출 요청한 보험사가 일치하는지 확인한다.

확인 항목:

- 동의서 또는 동의 기록에 지정된 보험사
- 병원이 제출 요청한 보험사
- 보험사 계정 또는 API 인증 상태

### 11.3 진료기록 무결성 검증

병원이 등록한 진료기록이 제출 시점에 임의로 변경되지 않았는지 확인한다.

확인 항목:

- 최초 등록 시 저장한 진료기록 해시
- 제출 요청 시점의 진료기록 해시
- 원문 또는 첨부 파일 변경 여부

### 11.4 제출 가능 상태 검증

해당 진료기록이 보험사 조회 가능 상태로 전환될 수 있는지 확인한다.

확인 항목:

- 중복 제출 여부
- 이전 검증 실패 또는 차단 상태 여부
- 보험사 포인트 잔액
- 보호자 동의 철회 또는 1년 유효기간 만료 이후 신규 조회 차단 여부

따라서 문서와 팀 커뮤니케이션에서는 "검증이 필요한 단계"라는 추상 표현보다 아래 표현을 우선 사용한다.

> 데이터 흐름은 MVP 구현상 `병원 -> 내부 시스템/플랫폼 -> 보험사`로 둔다. 병원은 진료기록과 제출 요청을 플랫폼에 등록하고, 보험사는 플랫폼 API 또는 화면으로 검증 완료 제출 패키지를 조회한다. 플랫폼은 제출 동의, 대상 보험사 일치 여부, 진료기록 무결성, 제출 가능 상태를 확인하는 검증 게이트 역할을 수행한다.

---

## 12. 검증 API 구성 의견

검증 API는 보험사의 보험금 산정이나 지급 판단을 대신하는 API가 아니다. MVP에서 검증 API는 **보험사가 제출 건의 검증을 요청하면 플랫폼이 검증을 새로 실행하거나 최신 검증 결과를 산출한 뒤, 비식별 진료 검증 데이터와 무결성 대조 정보를 반환하는 보험사용 검증 API**로 정의한다.

따라서 API 설계의 중심은 “이 청구가 얼마를 받을 수 있는가?”가 아니라 **“이 보험사가 이 제출 건의 비식별 진료 검증 데이터를 지금 조회해도 되는가?”** 여야 한다.

### 12.1 검증 API가 확인해야 하는 핵심 항목

검증 API는 최소한 아래 항목을 확인한다.

| 검증 항목 | 확인 내용 | 실패 시 처리 |
| --- | --- | --- |
| 제출 요청 존재 여부 | 병원이 생성한 제출 요청인지 확인 | `SUBMISSION_NOT_FOUND` |
| 병원 유효성 | 제출 병원이 등록/활성 상태인지 확인 | `HOSPITAL_INVALID` |
| 보험사 유효성 | 대상 보험사가 등록/활성 상태인지 확인 | `INSURER_INVALID` |
| 보호자 동의 여부 | 해당 진료기록을 해당 보험사에 제출하는 동의가 있는지 확인 | `CONSENT_MISSING` |
| 동의 철회/만료 여부 | 동의가 철회되었거나 1년 유효기간이 만료되었는지 확인 | `CONSENT_REVOKED` 또는 `CONSENT_EXPIRED` |
| 대상 보험사 일치 | 동의 대상 보험사와 요청 보험사가 같은지 확인 | `INSURER_MISMATCH` |
| 진료기록 무결성 | 등록 시점 해시와 제출 시점 해시가 같은지 확인 | `RECORD_HASH_MISMATCH` |
| 중복/상태 검증 | 이미 제출 완료, 차단, 실패 확정 상태인지 확인 | `INVALID_SUBMISSION_STATUS` |
| 포인트 잔액 | 보험사의 검증 API 사용 포인트가 충분한지 확인 | `INSUFFICIENT_POINTS` |
| 감사 로그 생성 | 검증 요청과 결과를 추적 가능하게 기록 | 로그 실패 시 검증 성공 처리 금지 |

### 12.2 검증 API 요청에 들어갈 값

검증 요청은 원문 진료기록 전체를 다시 보내는 방식보다, 플랫폼에 이미 등록된 리소스 식별자를 기준으로 호출하는 방식이 적합하다.

필수 요청 값:

- `submissionId`: 병원이 생성한 제출 요청 ID
- `recordId`: 진료기록 ID
- `hospitalId`: 제출 병원 ID
- `insurerId`: 제출 대상 보험사 ID
- `consentId`: 보호자 동의 ID
- `recordHash`: 제출 시점의 진료기록 해시
- `requestedBy`: API 호출 주체
- `requestedAt`: 검증 요청 시각

선택 요청 값:

- `claimReferenceId`: 보험사 또는 병원 내부 청구 참조 ID
- `petId`: 반려동물 ID
- `guardianId`: 보호자 ID
- `attachmentHashes`: 첨부 파일별 해시 목록
- `idempotencyKey`: 5분 이내 동일 재시도 식별 키. 같은 보험사가 같은 키로 재시도하면 기존 결과를 반환하고 추가 차감/적립하지 않음

MVP에서는 개인정보와 원문 진료기록을 검증 API 요청 본문에 과도하게 포함하지 않는다. 원문 또는 첨부 파일은 별도 저장소에 두고, 검증 API는 식별자와 해시 중심으로 동작한다.

### 12.3 검증 API 응답에 들어갈 값

검증 API 응답은 보험사가 후속 조회 가능 여부를 판단할 수 있도록 명확한 결과와 실패 사유를 반환해야 한다.

필수 응답 값:

- `verificationId`: 검증 결과 ID
- `submissionId`: 제출 요청 ID
- `status`: `PASSED` 또는 `FAILED`
- `canInsurerAccessRecord`: 보험사 조회 가능 여부
- `failureReasons`: 실패 사유 코드 목록
- `verifiedChecks`: 수행된 검증 항목 목록
- `recordHash`: 검증에 사용된 진료기록 해시
- `consentSnapshot`: 검증 시점의 동의 상태 요약
- `deidentifiedVerificationData`: 비식별 진료 검증 데이터
- `pointsCharged`: 차감된 보험사 포인트
- `hospitalCreditAccrued`: 적립된 병원 운영 크레딧
- `verifiedAt`: 검증 완료 시각
- `auditLogId`: 감사 로그 ID

응답 예시는 다음과 같은 의미 구조를 가진다.

```json
{
  "verificationId": "ver_001",
  "submissionId": "sub_001",
  "status": "PASSED",
  "canInsurerAccessRecord": true,
  "failureReasons": [],
  "verifiedChecks": [
    "CONSENT_VALID",
    "INSURER_MATCHED",
    "RECORD_HASH_VALID",
    "POINTS_CHARGED"
  ],
  "recordHash": "sha256:...",
  "deidentifiedVerificationData": {
    "treatmentCost": 120000,
    "treatmentCodes": ["EXAM_BASIC"],
    "diagnosisCodes": ["DX_SAMPLE"],
    "treatmentDate": "2026-05-15",
    "hospitalId": "hos_001",
    "insurerId": "ins_001"
  },
  "consentSnapshot": {
    "consentId": "con_001",
    "status": "ACTIVE",
    "insurerId": "ins_001"
  },
  "pointsCharged": 1,
  "hospitalCreditAccrued": 1,
  "verifiedAt": "2026-05-15T00:00:00Z",
  "auditLogId": "audit_001"
}
```

### 12.4 MVP에서 필요한 API 엔드포인트

MVP에서는 검증 API를 아래 정도로 제한하는 것이 좋다.

| API | 호출 주체 | 목적 |
| --- | --- | --- |
| `GET /submissions/{submissionId}/package` | 보험사 | 검증 완료 제출 패키지 조회. 별도 과금 없음 |
| `POST /submissions/{submissionId}/verification` | 보험사 | 제출 건 검증 실행 또는 최신 검증 결과 산출 후 비식별 진료 검증 데이터 반환. 성공 시 포인트 차감/크레딧 적립 |
| `GET /verifications/{verificationId}` | 보험사, 관리자 | 보험사가 본인이 호출한 검증 결과와 비식별 진료 검증 데이터 조회 |
| `GET /verifications/{verificationId}/deidentified-data` | 보험사 | 비식별 진료 검증 데이터 별도 조회 |
| `POST /internal/submissions/{submissionId}/verify` | 플랫폼 내부 또는 운영자 | 내부 워커, 재처리, 운영자 보정용 검증 실행 |
| `GET /verifications/{verificationId}/audit` | 관리자 | 검증 관련 감사 로그 조회 |

보험사용 검증 API 호출 권한은 보험사로 한정한다. 제출 패키지 조회와 검증 API 호출은 별도 과금하지 않으며, 과금/포인트 차감은 검증 API가 성공하고 비식별 진료 검증 데이터가 정상 반환되는 경우에만 발생한다. 검증 실패, 권한 없음, 포인트 부족 응답은 과금 대상이 아니다.

### 12.5 검증 API 상태값

검증 및 접근 상태값은 최소한 아래로 제한한다. 세부 상태 머신은 `## 13. MVP 세부 운영 정책`을 따른다.

- `PENDING`: 검증 전 또는 진행 중
- `PASSED`: 검증 통과, 보험사 조회 가능
- `FAILED`: 검증 실패, 보험사 조회 불가
- `PENDING_PAYMENT`: 보험사 포인트 부족으로 성공 응답 제공 대기
- `BLOCKED`: 동의 철회, 기관 비활성화, 운영자 차단, 권한 문제 등으로 조회 불가
- `SUPERSEDED`: 새 제출 패키지 버전 생성으로 기존 버전 대체
- `DELETED_BY_CONSENT_WITHDRAWAL`: 동의 철회로 제출 패키지 삭제
- `EXPIRED`: 동의 또는 제출 요청 유효기간 만료

### 12.6 검증 API가 하지 말아야 할 것

MVP 검증 API는 아래 기능을 수행하지 않는다.

- 보험금 산정
- 보험금 지급 가능 여부 판단
- 보험 약관 해석
- 질병/진료 코드의 보험 보장 여부 판단
- 보험사별 심사 규칙 적용
- 보호자에게 포인트 또는 리워드 지급
- 원문 진료기록 또는 첨부 파일 본문 반환
- 원문 진료기록의 의료적 타당성 판단

이 경계를 명확히 해야 플랫폼이 보험 심사자가 아니라 **제출 패키지 접근 권한과 비식별 진료 검증 데이터의 신뢰성·동의·무결성을 통제하는 검증 게이트**라는 점을 팀원들이 일관되게 이해할 수 있다.

## 13. MVP 세부 운영 정책

아래 정책은 `.omx/plans/Solved.md`의 확정 사안을 MVP 구현 기준으로 반영한 것이다.

### 13.1 포인트 차감 세부 정책

- 기본 차감 단위는 검증 API 성공 호출 1회당 보험사 포인트 1점이다.
- 포인트 부족은 제출 요청 자체의 검증 실패가 아니라 결제/사용권 대기 상태로 처리한다.
- 포인트 부족 시 `SubmissionStatus=PENDING_PAYMENT`, `VerificationStatus=BLOCKED`, 실패 코드는 `INSUFFICIENT_POINTS`로 기록한다.
- 포인트 부족, 권한 없음, 검증 실패, 호출 제한 응답은 과금 대상이 아니며 병원 크레딧 적립 대상도 아니다.
- 동일 제출 요청이라도 새 검증 API 성공 호출이면 매번 1점을 차감한다.
- 단, 같은 보험사가 같은 `Idempotency-Key`로 5분 이내 재시도한 요청은 기존 결과를 반환하고 추가 차감하지 않는다.
- 보험사 조직 단위 기본 호출 제한은 분당 60회로 둔다.
- 동일 제출 요청에 대해 10분 내 3회를 초과하는 성공 호출이 발생하면 이상 호출로 표시하고 운영자 검토 대상으로 남긴다.
- 포인트 차감 취소는 삭제가 아니라 `POINT_REVERSAL` 역거래로만 처리한다.
- 포인트 차감 취소는 플랫폼 장애, 잘못된 응답, 운영자 보정이 확인된 경우에만 허용하며, 요청 가능 기간은 차감 시점부터 7일이다.

### 13.2 병원 운영 크레딧 세부 정책

- 기본 적립 단위는 검증 API 성공 호출 1회당 병원 운영 크레딧 1점이다.
- 신규 제출, 정정, 보완 업데이트 모두 동일하게 검증 API 성공 호출 1회당 1점을 적립한다.
- 동일 제출 요청 반복 검증 API 성공 호출도 매번 1점을 적립한다.
- 단, 같은 보험사가 같은 `Idempotency-Key`로 5분 이내 재시도해 기존 결과를 반환받은 경우에는 추가 적립하지 않는다.
- 병원 크레딧 유효기간은 적립일로부터 12개월이다.
- 만료된 병원 크레딧은 `CREDIT_EXPIRED` 거래로 소각한다.
- 고급 SaaS 기능 차감 단위는 기능 1개당 30일 사용권 10크레딧으로 한다.
- 자체 웹사이트 배너 홍보 차감 단위는 기본 배너 7일 노출 20크레딧, 메인 배너 7일 노출 50크레딧으로 한다.
- 배너 홍보는 운영자 승인을 필수로 하며, 의료 효과 보장, 보험금 지급 보장, 비교 우위 과장 표현을 허용하지 않는다.
- 플랫폼 장애로 고급 SaaS 기능 또는 배너 홍보가 제공되지 않은 경우 `CREDIT_REVERSAL`로 복원한다.
- 병원의 단순 변심 취소는 서비스 시작 전 전액 복원, 서비스 시작 후 남은 기간 기준 일할 복원으로 처리한다.

### 13.3 보호자 동의 철회/만료 세부 정책

- 동의 만료 알림은 만료 30일 전, 7일 전, 1일 전에 보호자와 병원에 보낸다.
- 보험사에는 해당 보험사가 접근 가능한 활성 제출 요청이 있는 경우에만 동의 만료 예정 알림을 보낸다.
- 동의 철회 이벤트는 병원과 해당 제출 대상 보험사에 5분 이내 비동기 알림으로 전달한다.
- 철회 또는 만료 즉시 제출 패키지 신규 조회, 원문/첨부 신규 접근, 검증 API 신규 조회를 차단한다.
- 철회 후 재동의는 새 동의 이벤트로 기록한다.
- 재동의가 발생해도 철회로 삭제된 제출 패키지를 자동 복원하지 않는다.
- 재동의 후 보험사 제출이 필요하면 새 제출 요청과 새 제출 패키지를 생성한다.
- 제출 패키지는 철회 즉시 논리 삭제하고 30일 이내 물리 삭제한다.
- 법적 보존 또는 분쟁 보존 플래그가 있는 경우 물리 삭제를 보류하되, 외부 조회 권한은 계속 차단한다.
- 철회 후 감사 목적 내부 조회는 메타데이터와 감사 로그 중심으로 제한한다.
- 원문/첨부 또는 삭제 보류 제출 패키지에 대한 운영자 예외 조회는 2인 승인과 사유 입력을 필수로 한다.

### 13.4 제출 패키지 구현 세부 정책

- 제출 패키지는 원문 진료기록 또는 첨부 파일 본문을 API 응답에 직접 포함하지 않고, 접근 URL만 제공한다.
- 원문/첨부 접근 URL은 서명된 단기 URL로 발급한다.
- 접근 URL 기본 만료 시간은 10분이다.
- 접근 URL은 제출 대상 보험사 조직의 권한 있는 사용자에게만 유효하다.
- 접근 URL은 기본 1회 다운로드 후 만료된다. 다운로드 실패 또는 만료 시 권한 재검증 후 재발급한다.
- 제출 패키지 조회 권한은 제출 대상 보험사의 `CLAIM_REVIEWER`와 `CLAIM_MANAGER` 역할로 제한한다.
- 플랫폼 운영자 예외 조회는 `SUPPORT_ADMIN` 이상 권한, 사유 입력, 2인 승인, 감사 로그 기록이 있을 때만 허용한다.
- 제출 패키지 조회 API와 검증 API는 별도 엔드포인트와 별도 화면 흐름으로 분리한다.
- 제출 패키지 조회는 심사용 원문/첨부 접근 흐름이고, 검증 API는 무결성 대조용 비식별 진료 검증 데이터 조회 흐름이다.
- 제출 패키지는 불변 버전으로 관리한다.
- 병원이 제출 후 데이터를 업데이트하면 기존 제출 패키지를 덮어쓰지 않고 새 패키지 버전을 생성한다.
- 보험사는 기본적으로 최신 유효 버전만 조회한다.
- 이미 조회된 이전 버전은 감사 이력으로만 보존하고, 동의 철회/만료 또는 무효화 이후에는 재조회할 수 없다.
- 진료기록 해시와 첨부 파일 해시는 SHA-256으로 생성한다.
- 해시는 원문 등록 시점과 제출 패키지 버전 생성 시점에 생성·기록한다.
- 원문 또는 첨부 파일이 변경되면 기존 제출 패키지는 `SUPERSEDED` 처리하고 새 버전을 생성한다.
- 제출 패키지 보관 기간은 동의 유효기간과 동일하게 최대 1년으로 한다.
- 감사 로그는 제출 패키지 삭제 이후에도 5년간 보관한다.

### 13.5 상태 머신 세부 정책

ConsentStatus:

- `ACTIVE`: 유효기간 내 동의가 살아 있는 상태
- `REVOKED`: 보호자가 동의를 철회한 상태
- `EXPIRED`: 동의 유효기간 1년이 만료된 상태

SubmissionStatus:

- `DRAFT`
- `SUBMITTED`
- `VERIFICATION_PENDING`
- `VERIFICATION_PASSED`
- `VERIFICATION_FAILED`
- `PENDING_PAYMENT`
- `BLOCKED`
- `SUPERSEDED`
- `DELETED_BY_CONSENT_WITHDRAWAL`

VerificationStatus:

- `PENDING`
- `PASSED`
- `FAILED`
- `BLOCKED`
- `EXPIRED`

PackageAccessStatus:

- `AVAILABLE`
- `BLOCKED_BY_CONSENT`
- `BLOCKED_BY_PERMISSION`
- `SUPERSEDED`
- `DELETED`
- `EXPIRED`

- `AVAILABLE`
- `BLOCKED_BY_CONSENT`
- `BLOCKED_BY_PERMISSION`
- `BLOCKED_BY_POINTS`

상태 전이 원칙:

- 모든 상태 전이는 감사 로그를 남긴다.
- 동의 철회 시 `ConsentStatus=REVOKED`, `PackageAccessStatus=DELETED`, `VerificationDataAccessStatus=BLOCKED_BY_CONSENT`로 전환한다.
- 동의 만료 시 `ConsentStatus=EXPIRED`, `PackageAccessStatus=EXPIRED`, `VerificationDataAccessStatus=EXPIRED`로 전환한다.
- 포인트 부족 시 제출 요청은 삭제하지 않고 `SubmissionStatus=PENDING_PAYMENT`로 둔다.
- 원문 또는 첨부 업데이트 시 기존 제출 패키지는 `SUPERSEDED` 처리하고 새 버전을 만든다.
- 체인 데이터는 삭제하지 않으며, 플랫폼 상태는 체인 보존 여부와 별도로 접근 가능 여부를 표현한다.

### 13.7 보험사 심사 상태 기록 세부 정책

- 허용 상태는 `RECEIVED_BY_INSURER`, `UNDER_REVIEW`, `APPROVED_BY_INSURER`, `REJECTED_BY_INSURER`, `CLOSED`로 제한한다.
- 보호자와 병원에는 `RECEIVED_BY_INSURER`, `UNDER_REVIEW`, `CLOSED` 수준의 단순 진행 상태만 노출한다.
- `APPROVED_BY_INSURER`와 `REJECTED_BY_INSURER`는 보험사가 명시적으로 외부 노출을 허용한 경우에만 보호자/병원에게 노출한다.
- 보험금 산정 금액, 약관 판단 근거, 보험사 내부 심사 메모 전문, 지급 거절의 상세 법적 사유, 내부 리스크 스코어는 저장하지 않는다.
- 보험사 심사 상태 변경은 모두 감사 로그로 남긴다.
- 보험사 심사 상태는 보험사 포인트 차감, 병원 크레딧 적립, 병원 크레딧 소각과 연결하지 않는다.
- 보험사 심사 상태 변경 실패 또는 승인/거절 결과는 이미 발생한 검증 API 성공 호출 과금과 병원 크레딧 적립을 되돌리지 않는다.
