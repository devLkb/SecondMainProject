# 프론트엔드 ↔ 백엔드 연결 작업 정리

> 작업일: 2026-05-20
> 목표: 프론트의 가짜값(하드코딩) 제거 + 백엔드 연동, 연결 안 된 부분 전부 연결
> 원칙: 프론트 코드는 가짜값·API 연결 부분만 수정, 나머지는 백엔드를 프론트에 맞춰 수정
> 검증: **백엔드 클린 컴파일 성공 + 프론트엔드 빌드 성공** (런타임/DB 테스트는 미실시)

---

## 1. 백엔드 — 신규 구축

### 1-1. 회원 본인 프로필 `/api/users/me`
| 파일 | 내용 |
|---|---|
| `petchainLOGIN/controller/UserController.java` | `GET /api/users/me`, `PATCH /api/users/me` |
| `petchainLOGIN/service/UserProfileService.java` | 역할(보호자/병원/보험사)별 프로필 조회·수정 |
| `petchainLOGIN/dto/response/MeResponse.java` | userId, memberType, memberNumber, name, email, phone, region, orgName, fabricOrgId |
| `petchainLOGIN/dto/request/UpdateMeRequest.java` | name, phone, email, region (전부 선택값) |

- 프론트는 회원 본인 id를 모르고 `userId`만 갖고 있어 `me` 사용을 전제로 설계.

### 1-2. 병원 환자 조회 `/api/pets/{petId}`
| 파일 | 내용 |
|---|---|
| `petchainLOGIN/controller/PetController.java` | `GET /api/pets/{petId}` 추가 |
| `petchainLOGIN/service/PetService.java` | `getPetDetail()` — 펫 + 진료기록 조회 (DB id 또는 펫번호 `A-xxxxxxxx`) |
| `petchainLOGIN/dto/response/PetDetailResponse.java` | 펫 기본정보 + `RecordItem` 목록 |
| `petchainDB/repository/MedicalRecordRepository.java` | `findByPet_IdOrderByTreatmentDateDesc` 추가 |

- 기존엔 `GET /api/pets/{id}` 엔드포인트 자체가 없어 병원 환자조회가 항상 로컬 폴백으로 동작했음.

### 1-3. 이상 신고(Flag) 시스템 — 전부 신규
| 파일 | 내용 |
|---|---|
| `petchainDB/entity/RecordFlag.java` | 신고 엔티티 (펫/병원/질병/진료비 스냅샷 보관) |
| `petchainDB/repository/RecordFlagRepository.java` | 조회·상태별 카운트 |
| `petchainAPI/dto/flag/FlagDtos.java` | CreateFlagRequest, ResolveFlagRequest, FlagResponse |
| `petchainAPI/service/FlagService.java` | 생성(보험사)·조회(플랫폼)·처리(플랫폼) |
| `petchainAPI/controller/FlagController.java` | `POST /api/flags`, `GET /api/flags`, `POST /api/flags/{flagId}/resolve` |

- `ddl-auto=update`라 `record_flags` 테이블은 서버 기동 시 자동 생성됨.

### 1-4. 플랫폼 Org 관리·모니터링 — 전부 신규
| 파일 | 내용 |
|---|---|
| `petchainAPI/dto/admin/PlatformDtos.java` | OrgResponse, MonitorResponse |
| `petchainAPI/service/PlatformAdminService.java` | Org 목록/승인, 모니터링 집계 |
| `petchainAPI/controller/PlatformAdminController.java` | `GET /api/admin/orgs`, `POST /api/admin/orgs/{orgId}/approve`, `GET /api/admin/monitor` |

- 승인 시 병원/보험사 `isActive=true` + 연결 `User.status=active` 처리.

## 2. 백엔드 — 기존 수정

| 파일 | 변경 |
|---|---|
| `petchainLOGIN/config/SecurityConfig.java` | CORS 허용 메서드에 `PATCH` 추가 (프론트 `/users/me` PATCH가 차단돼 있었음) |
| `petchainLOGIN/dto/response/PetResponse.java` | `getId()` 추가 — 프론트가 `p.id`로 읽으므로 `petId`와 동일 값 노출 |
| `petchainAPI/dto/record/RecordDtos.java` | `RecordSummaryResponse`에 petName·treatmentCost·코드·memo·onChainStatus 추가 |

| `petchainAPI/dto/consent/ConsentDtos.java` | `ConsentResponse`에 petName·hospitalName·insurerName·disease·cost·date 추가 |
| `petchainAPI/service/ConsentService.java` | `toResponse()` 보강 + `listConsents`가 `guardianId/insurerId=me` 지원 |

- 목적: 프론트가 진료기록·동의 카드를 그대로 렌더링하는데 필요한 필드를 백엔드가 내려주지 않아 빈 값으로 표시되던 문제 해결.

## 3. 프론트엔드 — 가짜값 제거 + API 연결

> 프론트는 "하드코딩된 가짜값"과 "API 연결 부분"만 수정. 레이아웃·스타일·로직은 미변경.

### 3-1. `GuardianDash.jsx` (보호자)
- 사이드바 `홍길동` 하드코딩 → `state.userName` (백엔드 `/users/me`)
- 내 정보 탭 `홍길동`·`hong@email.com`·`010-1234-5678` 하드코딩 제거 → `/users/me` 값 사용
- 내 정보 저장 → 실제 `PATCH /api/users/me` 호출 (기존엔 로컬 상태만 갱신)
- 진료기록·동의 조회를 `guardianId=me`로 변경 → 본인 데이터만 조회 (기존엔 전체 조회)

### 3-2. `InsuranceDash.jsx` (보험사)
- 포인트 잔액: `/insurers/me/points/balance` 연동
- 동의 목록: 응답 배열 언래핑 버그 수정 (`{consents:[...]}` 처리)
- 포인트 거래이력: `/insurers/me/points/transactions` 연동 → `+1,000` ISSUE 하드코딩 행 제거
- `충전 총량` 하드코딩 `1000` → 실제 issue 거래 합계
- 검증(`handleVerify`): `POST /submissions` → 실제 `submissionId` 확보 후 `verification` 호출
- 심사결과(`handleReview`): `POST /submissions/{id}/claim-status` 연동
- 이상신고(`handleFlag`): `POST /api/flags` 연동

### 3-3. `Platform.jsx` (플랫폼 관리자)
- 기존: 전체가 mock, `apiFetch` import조차 없었음
- Org 목록·이상신고·모니터링 집계를 진입 시 백엔드에서 로드
- Org 승인(`handleApprove`): `POST /admin/orgs/{id}/approve`
- 포인트 발행(`handleIssue`): `POST /admin/insurers/{id}/points/issue` — 대상 보험사 select를 실데이터로 채움, 메모 입력 연결
- 이상신고 처리(`handleResolve`): `POST /flags/{flagId}/resolve`

### 3-4. `HospitalDash.jsx` (병원)
- 크레딧 현황 탭: `REC-2024-0041/0040` 하드코딩 행 제거 → `/credits/transactions?hospitalId=me` 연동
- 감사 로그 탭: 하드코딩 행 2건 제거 (실제 세션 데이터만 표시)
- 조직 정보 탭: 병원명 하드코딩(`동물병원`) → `/users/me` 연동
- 동의 목록 조회: 응답 배열 언래핑 버그 수정
- 환자 조회: 신규 `GET /api/pets/{id}` 엔드포인트에 연결

## 4. 연결하지 않은 부분 (의도적)

| 항목 | 사유 |
|---|---|
| 병원 OrgTab 채널 구성원, 해시 미리보기 `sha256:a3f2b9c1...`, on_chain 상태 | Hyperledger Fabric 네트워크 토폴로지 — 백엔드에 해당 개념 없음 (개념적 UI 유지) |
| 보험사 `CHANNEL_INFO` 채널 정보 | 위와 동일 |
| 플랫폼 포인트 탭 "보험사별/병원 크레딧 현황" 소표 | per-org 목록 엔드포인트 부재 — 일부만 실데이터 |
| 보호자 보험계약 등록 모달, 청구상태 타임라인 | 보험계약 생성 엔드포인트 부재 — 로컬 유지 |
| 동의 생성(`handleToggle`) 신규 케이스 | API 호출은 연결됨. 단, 기존 claim이 없는 신규 동의는 대상 보험사 식별이 모호한 도메인 설계 이슈 잔존 (`API_계약불일치_점검.md` #2 참고) |

## 5. 연결 점검 결과 (데이터 흐름 추적)

> 백엔드 클린 컴파일 · 프론트 빌드 · ESLint 모두 통과 상태에서 흐름을 1건씩 추적 점검함.

### 5-1. 점검 중 발견 → 수정한 문제

| 문제 | 내용 | 조치 |
|---|---|---|
| `ConsentResponse`에 `petId` 누락 | 프론트 `loadConsents`가 `c.petId`를 읽어 `state.consents`에 저장하는데 백엔드가 해당 필드를 안 내려줘 항상 `undefined`였음 (검증 API의 `petId`는 필수값이 아니라 크래시는 없었음) | `ConsentDtos.ConsentResponse` + `ConsentService.toResponse`에 `petId` 추가, 재컴파일 성공 |
| `GuardianDash` 빈 `catch {}` 3건 | 기존부터 있던 빈 블록이 `npm run lint`를 깨고 있었음 (`handleToggle`/`handleRegionSave`/`handleAddPet`) | 주석 추가로 정리 → ESLint 통과 |

### 5-2. 추적 검증 완료 (이상 없음)

- **apiFetch 언래핑** — `ApiResponse<T>`(`{data,traceId}`)는 자동 언랩, 신규 컨트롤러(User/Pet/Flag/PlatformAdmin)는 raw 반환이라 그대로 통과
- **경로 충돌 없음** — `PlatformAdminController(/admin/orgs)` vs `AdminController(/admin/insurers/...)`, `GET /pets` vs `GET /pets/{petId}` 모두 구분됨
- **`me` 식별자 해석** — 식별자가 `null`일 때 `"me".equalsIgnoreCase(null)`은 `false` → 엉뚱한 `xxxByActor` 호출 안 됨 (병원이 `/consents` 호출 시 `guardianByActor` 예외 미발생)
- **검증 플로우** — `handleVerify`가 실제 `submissionId` 확보 후 `verification` 호출, 실패 시 catch에서 보존. `handleReview` 정규식 `/^CLM-\d/`이 실제 claimId와 폴백 id를 정확히 구분
- **요청 검증** — 모든 요청 body가 DTO 필드와 일치, `@JsonIgnoreProperties(ignoreUnknown=false)` DTO들도 미지 필드 없음
- **인증/스코프/CORS** — `/admin/**`·`/flags`·`/users/me` 인증 필요, 플랫폼 admin은 `platform→ADMIN`으로 `requireAdmin` 통과, CORS `PATCH` 추가(프리플라이트는 Security CorsFilter가 인가 전 처리)
- **NPE 위험** — 접근하는 FK는 모두 `nullable=false`, 코드 리스트는 `List.of()` 폴백
- **기존 플로우 영향 없음** — DTO 필드 추가는 가산적, `me` 처리는 리터럴 `"me"`에서만 발동 → 기존 식별자 경로 그대로 동작

### 5-3. 버그는 아니지만 알아둘 한계

| 항목 | 내용 |
|---|---|
| 검증 버튼 더블클릭 | `handleVerify`가 API await 후 탭 전환 → 1회 왕복 동안 행이 클릭 가능, 빠른 더블클릭 시 중복 제출 가능 (저위험, 기존 코드도 가드 없음) |
| 병원 `/consents` 스코프 | 병원은 전체 동의 목록을 받음(병원 필터 엔드포인트 없음) — 크래시 없음, 표시 범위만 넓음 |
| Platform 신고 목록 | 진입 시 1회 로드 → 보험사가 새로 신고해도 Platform 새로고침 전엔 미표시 |
| 포인트 잔액 낙관적 갱신 | 검증 시 로컬 `ptBalance -1`은 즉시, 백엔드 동기화는 다음 마운트 시 — 기존 패턴 |
