# 프론트백 연결 확인 가이드

> 작성일: 2026-05-20
> 대상: 프론트엔드 ↔ 백엔드 연결이 실제 데이터 흐름까지 살아 있는지 화면에서 직접 확인
> 사용 도구: 브라우저(DevTools Network 탭) · MySQL Workbench(또는 `mysql -u root -p`) · Postman/curl(선택)

이 가이드는 **백엔드를 띄우지 않은 정적 분석에서 검증할 수 없는 부분**을 화면에서 클릭하면서 확인하는 순서입니다.
모든 단계는 *위에서 아래로 순서대로* 실행해야 합니다. 한 단계라도 실패하면 그 다음 단계는 보통 실패합니다.

## 0. 사전 점검 (서버 띄우기)

### 0-1. MySQL & 백엔드 기동
```powershell
# 프로젝트 루트
cd c:\Users\규라\workspace\pointpro
docker compose up -d mysql                # MySQL 컨테이너만 먼저
cd be\backend
.\gradlew.bat bootRun                     # 백엔드 (8080)
```
- 콘솔 마지막 줄에 `Started BackendApplication in ... seconds` 가 나오면 OK.
- 실패 시 [docker-compose.yml](docker-compose.yml) 의 DB 환경변수와 [be/backend/src/main/resources/application.properties](be/backend/src/main/resources/application.properties) 의 `spring.datasource.url` 이 같은 호스트·포트인지 확인.

### 0-2. 프론트엔드 기동
```powershell
cd c:\Users\규라\workspace\pointpro\fe\petchain
npm run dev                               # Vite (5173)
```
- 브라우저: `http://localhost:5173` 접속.

### 0-3. 신규 테이블 자동 생성 확인 (가장 흔히 빠뜨리는 단계)
이번 작업에서 추가된 테이블 `record_flags` 가 `ddl-auto=update` 로 자동 생성되어야 합니다.
```sql
USE petchain;
SHOW TABLES LIKE 'record_flags';
DESC record_flags;
```
- 컬럼이 `id, record_id, verification_id, reason_code, note, status, reported_by_insurer_id, pet_name, hospital_name, disease, cost, resolve_code, resolve_note, resolved_at, created_at, updated_at` 순서로 나오면 OK.
- 안 나오면 백엔드 로그에서 `Hibernate: create table record_flags ...` 가 찍혔는지 확인.

### 0-4. 기존 point_balances 1회 패치 (낙관락 컬럼)
이전 작업에서 `version` 컬럼이 추가되어 있는데 기존 행이 null 이면 검증 시 OptimisticLock 예외가 납니다.
```sql
UPDATE point_balances SET version = 0 WHERE version IS NULL;
```

## 1. 보호자 (Guardian) — `/users/me`, `/pets`, `/records`, `/consents`

### 1-1. 로그인 → 사이드바·내 정보가 백엔드 값으로 채워지는지
1. `보호자 로그인` 으로 진입.
2. 사이드바에 표시되는 이름이 **회원가입 시 입력한 이름** 인지 확인 (구버전은 `홍길동` 고정이었음).
3. 좌측 메뉴 **내 정보** 탭으로 이동 → 이름·이메일·전화·지역이 모두 **DB 값**으로 채워져 있어야 함.
4. DevTools Network: `GET /api/users/me` 가 200 응답이고 body 가 `{userId, memberType:'user', memberNumber, name, email, phone, region}` 형태인지 확인.

### 1-2. 내 정보 수정 → 실제 PATCH 가 나가는지
1. **내 정보** 탭에서 전화번호를 임의로 바꾸고 `저장` 클릭.
2. Network 탭에서 `PATCH /api/users/me` 요청이 200 응답을 받는지 확인.
3. 페이지 새로고침 후 다시 **내 정보** 진입 → 바꾼 값이 그대로 보여야 함.
4. DB 확인:
   ```sql
   SELECT id, name, phone, email, address FROM guardians WHERE user_id = <본인 userId>;
   ```
   `address` 가 화면의 거주지역과 일치해야 함.

### 1-3. 반려동물 등록 → `POST /api/pets`
1. **내 반려동물** 탭 → `+ 반려동물 등록` → 폼 작성 후 등록.
2. Network: `POST /api/pets` 201 응답 → 응답 body 에 `petId`(숫자), `petNumber`(A-xxxxxxxx) 포함.
3. 등록 직후 곧바로 `GET /api/pets` 가 다시 호출되어 목록이 실데이터로 갈아끼워지는지 확인.
4. DB:
   ```sql
   SELECT id, pet_number, name, species FROM pets WHERE guardian_id = <본인 guardian id> ORDER BY id DESC LIMIT 5;
   ```

### 1-4. 진료기록·동의 목록 → `me` 치환이 잘 되는지
1. 같은 보호자로 진료기록·동의가 1건이라도 있어야 의미가 있음 (없으면 §2 병원 플로우 먼저 진행).
2. **동의 관리** 탭 진입 → `GET /api/consents?guardianId=me` 요청 확인.
3. 응답에서 다른 보호자의 동의가 섞여 있지 않은지 확인 — 본인 동의만 와야 함.

### 1-5. 동의 토글 (활성 → 철회) → `POST /api/consents/{consentId}/revoke`
1. 동의가 active 인 행 토글 OFF.
2. Network: `POST /api/consents/{claimId}/revoke` 가 200 응답.
3. DB:
   ```sql
   SELECT claim_id, consent_status, claim_status FROM claim_packages ORDER BY id DESC LIMIT 5;
   ```
   해당 행의 `consent_status` 가 `revoked` 로 바뀌어 있으면 OK.

## 2. 병원 (Hospital) — `/users/me`, `/pets/{id}`, `/records`, `/credits`

### 2-1. 조직 정보 탭 → `GET /api/users/me`
1. 병원 계정 로그인.
2. **조직 정보** 탭 → `Org ID` 가 `H-xxxxxxxx`, `병원명` 이 회원가입 시 입력한 이름과 일치하는지 확인.
3. Network: `GET /api/users/me` 200 응답 body 에 `memberType:'hospital'`, `orgName`, `fabricOrgId` 가 들어 있어야 함.

### 2-2. 환자 조회 → `GET /api/pets/{petId}` (이번 작업에서 새로 만든 엔드포인트)
1. **진료기록 등록** 탭 → 환자 조회 칸에 §1-3 에서 생성된 펫번호(`A-xxxxxxxx`) 입력 후 `조회`.
2. Network: `GET /api/pets/A-xxxxxxxx` 200.
3. 화면 표시 확인:
   - 펫 이름·종·품종·보험사가 채워짐.
   - **상단 카드의 PetChain ID 가 `A-xxxxxxxx` 형식 (숫자 아님)** ← 이번 수정 포인트. 숫자만 보이면 BE 의 `PetDetailResponse.petId` 가 다시 numeric 으로 돌아간 것.
4. 이전 진료기록 표가 있다면 응답 `records` 배열에서 채워지는지 확인 (없으면 §2-3 진료기록 등록 먼저).

### 2-3. 진료기록 등록 → `POST /api/records` (multipart)
1. 환자 조회 후 질병 코드·진료비·진료일을 입력하고 `🔗 원장에 기록` 클릭.
2. Network: `POST /api/records` (Content-Type: multipart/form-data) 201 응답 → body 에 `recordId, recordHash` 포함.
3. DB:
   ```sql
   SELECT record_id, detail_data_hash, total_cost, treatment_date FROM medical_records ORDER BY id DESC LIMIT 3;
   ```
   - `record_id` 형식: `REC-yyyy-NNNN`
   - `detail_data_hash` 가 `sha256:...` 또는 비슷한 64자 hex 로 채워져 있어야 함.

### 2-4. 크레딧 현황 탭 → `GET /api/credits/transactions?hospitalId=me`
1. **크레딧 현황** 탭 진입.
2. Network: `GET /api/credits/transactions?hospitalId=me&size=50` 200 응답.
3. 빈 응답이면 표가 "적립된 크레딧이 없습니다" 로 표시.
4. (선택) 검증 1건 통과시키면 크레딧이 +1 적립되어 표에 나타남 → §3-3 이후 다시 와서 확인.

### 2-5. 동의 목록 자동 불러오기
1. **진료기록 등록** 탭 상단에 `✅ 보호자 동의 N건 활성` 배지가 떠야 함.
2. Network: `GET /api/consents` 200, 응답이 `{consents:[...]}` 형태로 와야 함. 빈 배열이면 §1-5 의 동의가 active 인지 다시 확인.

## 3. 보험사 (Insurance) — `/insurers/me/points/*`, `/consents`, `/submissions`, `/flags`

### 3-1. 포인트 잔액 표시 → `GET /api/insurers/me/points/balance`
1. 보험사 로그인 → **포인트 현황** 탭.
2. Network: `GET /api/insurers/me/points/balance` 200, body `{insurerId, balance, updatedAt}`.
3. 잔액이 0 이면 §4-2 의 플랫폼 발행을 먼저 해야 함 (잔액 0 이면 검증 버튼이 disabled).

### 3-2. 동의 목록 → `GET /api/consents?insurerId=me`
1. **검증 목록** 탭.
2. 표에 본인 보험사로 신청된 active 동의만 표시되는지 확인.
3. 응답 body 의 한 항목에 **`recordHash` 필드가 sha256 값으로 채워져 있는지** 확인 ← 이번 수정 포인트. 없으면 BE `ConsentDtos.ConsentResponse` 가 옛 버전.

### 3-3. 검증 API → `POST /api/submissions` → `POST /api/submissions/{id}/verification`
1. **검증 목록** 표에서 한 행의 `검증 API →` 클릭.
2. Network 순서:
   - `POST /api/submissions` 201 → body `{submissionId, status:'SUBMITTED', ...}`
   - `POST /api/submissions/{submissionId}/verification` 200 → body `{verificationId, status:'PASSED', canInsurerAccessRecord:true, recordHash, ...}`
3. **PASSED 가 아니라 FAILED 가 나오면** §3-2 의 recordHash 가 안 내려오는 상태일 가능성 큼 (해시 미스매치).
4. DB:
   ```sql
   SELECT id, result, points_spent FROM verification_logs ORDER BY id DESC LIMIT 3;
   ```
   `result='verified'`, `points_spent=1` 이어야 함.
5. 포인트 잔액이 -1 됐는지 다시 §3-1 로 가서 확인.

### 3-4. 심사 결과 기록 → `POST /api/submissions/{id}/claim-status`
1. 검증 결과 카드에서 `✓ 승인` 또는 `✕ 반려` 클릭.
2. Network: `POST /api/submissions/{submissionId}/claim-status` 200, body `{submissionId, status:'APPROVED_BY_INSURER'|'REJECTED_BY_INSURER', updatedAt}`.
3. DB:
   ```sql
   SELECT claim_id, review_result, claim_status FROM claim_packages WHERE claim_id = '<submissionId>';
   ```
   `review_result`, `claim_status` 가 갱신되어야 함.

### 3-5. 이상 신고 → `POST /api/flags` (이번 작업에서 새로 만든 엔드포인트)
1. 검증 결과에서 `⚠️ 이상 신고` 클릭 → 사유 선택 → `플랫폼에 이상 신고 전달`.
2. Network: `POST /api/flags` 201, body `{flagId:'FLAG-<n>', recordId, reasonCode, reasonLabel, status:'PENDING', ...}`.
3. DB:
   ```sql
   SELECT id, record_id, reason_code, status, pet_name, hospital_name, cost FROM record_flags ORDER BY id DESC LIMIT 3;
   ```
   진료기록이 DB 에 있다면 `pet_name/hospital_name/cost` 가 스냅샷으로 채워져 있어야 함.

## 4. 플랫폼 관리자 (Platform) — `/admin/orgs`, `/admin/monitor`, `/flags`

### 4-1. 진입 시 3개 호출 동시 발사
1. 플랫폼 로그인 (`admin` / `admin1234` — [application.properties](be/backend/src/main/resources/application.properties) 의 `admin.login-id`, `admin.password`).
2. Network 탭에서 진입 직후 다음 3개가 동시에 보여야 함:
   - `GET /api/admin/orgs` → `[{id:'H-...'|'P-...', name, type:'병원'|'보험사', fabricOrg, date, status}, ...]`
   - `GET /api/flags` → `[{flagId, recordId, reasonCode, status, ...}, ...]`
   - `GET /api/admin/monitor` → `{totalOrgs, activeOrgs, pendingOrgs, verifyCount, totalFlags, pendingFlags, insurerPointBalance}`
3. **Org 관리** 탭 표에 회원가입한 병원/보험사가 모두 보여야 함. 안 보이면 `requireAdmin` 이 막은 것 — admin 계정으로 로그인했는지 확인.

### 4-2. Org 승인 → `POST /api/admin/orgs/{id}/approve`
1. `승인 대기` 인 Org 의 `승인` 버튼 클릭.
2. Network: `POST /api/admin/orgs/H-xxxxxxxx/approve` 200, body `{status:'active', ...}`.
3. DB:
   ```sql
   SELECT member_number, name, is_active FROM hospitals;
   SELECT member_number, name, is_active FROM insurance_companies;
   SELECT user_id, status FROM users WHERE status='active' ORDER BY id DESC LIMIT 5;
   ```
   해당 Org 의 `is_active=1`, 연결된 `users.status='active'` 가 되어야 함.

### 4-3. 포인트 발행 → `POST /api/admin/insurers/{id}/points/issue`
1. **포인트 발행** 탭에서 대상 보험사 select (실데이터로 채워짐) → 수량·메모 입력 → `발행 실행`.
2. Network: `POST /api/admin/insurers/P-xxxxxxxx/points/issue` 200, body `{insurerId, transactionId, issuedAmount, balance, ...}`.
3. 응답 `balance` 값이 §3-1 의 잔액과 일치해야 함.

### 4-4. 이상 신고 처리 → `POST /api/flags/{flagId}/resolve`
1. **이상 신고** 탭의 `검토 대기` 행에서 `처리하기` → 결과 선택 → `처리 완료로 기록`.
2. Network: `POST /api/flags/FLAG-<n>/resolve` 200, body `{flagId, status:'RESOLVED', resolveCode, resolvedAt, ...}`.
3. DB:
   ```sql
   SELECT id, status, resolve_code, resolved_at FROM record_flags ORDER BY id DESC LIMIT 3;
   ```

## 5. 전체 플로우 1회 통합 점검 (E2E)

순서대로 한 사이클 돌리면 1~4번 단계의 모든 연결이 한 번에 검증됩니다.

| 순번 | 역할 | 행동 | 확인 |
|---|---|---|---|
| 1 | 플랫폼 | 신규 가입 병원·보험사 모두 승인 (§4-2) | `users.status='active'` |
| 2 | 플랫폼 | 대상 보험사에 1000pt 발행 (§4-3) | 응답 `balance=1000` |
| 3 | 보호자 | 반려동물 등록 (§1-3) | DB `pets` 신규 행 |
| 4 | 병원 | 펫번호로 환자 조회 → 진료기록 등록 (§2-2, §2-3) | DB `medical_records` 신규 행 |
| 5 | 보호자 | 동의 토글 ON (해당 record) | `claim_packages.consent_status='active'` |
| 6 | 보험사 | 검증 API 호출 (§3-3) | `verification_logs.result='verified'`, 포인트 -1, 병원 크레딧 +1 |
| 7 | 보험사 | 심사 결과 `승인` (§3-4) | `claim_packages.review_result` 갱신 |
| 8 | 보험사 | 다른 record 에 이상 신고 (§3-5) | `record_flags.status='PENDING'` |
| 9 | 플랫폼 | 신고 처리 (§4-4) | `record_flags.status='RESOLVED'` |
| 10 | 병원 | 크레딧 현황 탭 (§2-4) | 표에 +1 ACCRUAL 행 |
| 11 | 보호자 | 동의 토글 OFF → 다시 보험사 검증 시도 | 검증 결과가 FAILED 또는 BLOCKED |

## 6. 자주 막히는 곳 체크리스트

1. **모든 호출 401 Unauthorized**
   - localStorage 의 `accessToken` 이 비어 있거나 만료. 다시 로그인.
2. **`/api/users/me` 가 500**
   - JWT 의 `sub` 가 숫자가 아니거나 회원 행이 삭제됨. `users.id` 와 토큰 `sub` 일치 확인.
3. **검증이 항상 FAILED (hash_mismatch)**
   - 동의 목록 응답에 `recordHash` 필드가 빠짐. BE `ConsentService.toResponse` 의 마지막 인자가 `record.getDetailDataHash()` 인지 확인.
4. **병원 환자 조회 ID 가 숫자**
   - `PetDetailResponse.petId` 가 `Long` 으로 돌아감. `PetService.getPetDetail` 의 생성자 인자 첫 3개가 `pet.getPetNumber()` 인지 확인.
5. **이상 신고가 안 보임 (Platform `/flags` 진입시)**
   - 1) 신고 한 적이 없거나, 2) `record_flags` 테이블 미생성. §0-3 확인.
6. **CORS 에러 (브라우저 콘솔에 "blocked by CORS policy")**
   - [SecurityConfig.java](be/backend/src/main/java/com/blockchain/backend/petchainLOGIN/config/SecurityConfig.java) 의 `app.cors.allowed-origins` 가 현재 프론트 Origin(`http://localhost:5173`)을 포함하는지 확인. PATCH 메서드가 허용 목록에 있는지도 확인.
